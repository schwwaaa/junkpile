Orientation

What Junkpile does #

Junkpile removes repeated setup work from creative desktop development. Instead of starting with an empty Tauri project and rebuilding graphics, media input, recording, control, and output plumbing yourself, you can begin with a working example that already owns the part of the application you need.

The examples are meant to be run, read, modified, and combined. They range from approachable WebView/WebGL projects to native Rust/wgpu projects for workloads that need more direct GPU or media control.

Desktop application shell

Tauri v1 and v2 package the project as a desktop application and determine configuration, permissions, plugins, window APIs, IPC conventions, and some window-integration constraints.

Where the graphics run

WebView/WebGL is the more accessible browser-style path. Native Rust/wgpu gives Rust direct ownership of pixels, textures, the render loop, and GPU resources when the application needs that control.

Connect the application

Camera, audio, files, MIDI, OSC, FFmpeg, NDI, Syphon, Spout, and other services connect the application to media, controllers, recorders, and external systems. They are integration layers, not synonyms for one renderer.

No fixed public total.The library is designed to grow. Documentation is organized around architectural tracks and capabilities rather than an advertised example count.
Quick start

Run one project before you change anything #

The fastest way into Junkpile is to find the example closest to your goal and prove that it works unchanged. That gives you a known-good baseline before your own code enters the picture.

  1. Choose the smallest example that already does the input, processing, or output job you need.
  2. Enter that project directory.
  3. Run npm install once for the project.
  4. Run npm run dev.
  5. Confirm the untouched baseline before editing.
Example: Native A/V recorder
git clone https://github.com/schwwaaa/junkpile.git
cd junkpile/wgpu/43-wgpu-av-recorder
npm install
npm run dev

Install the distribution's Tauri/WebKitGTK development packages and a functional Vulkan or supported GPU driver stack.

Choose a track

Choose the simplest starting point for the job #

Do not choose a track because one sounds more advanced. Choose it based on what your application actually needs. WebView projects are often faster to understand and modify; native wgpu becomes useful when direct GPU ownership, compute, high-resolution rendering, or tighter native-media integration matters.

p5.js / browser-media experimentation Tauri v1 or v2 WebView
Current Tauri permissions, dialogs, window APIs Tauri v2 WebView
Explicit GPU resources / compute Native wgpu
Current high-resolution native render/record references Native wgpu series
Current dedicated NDI / Syphon / Spout sender references Native wgpu I/O series; the transports themselves are not wgpu-only
Fast creative application parity Compare the WebView example with its native counterpart where one exists

Tauri 2 + native Rust/wgpu

Use native wgpu when the renderer needs more direct control #

Use the native collection when the application benefits from Rust owning the render loop and GPU resources directly—for example compute workloads, 3D, high-resolution rendering, native video paths, recording, or explicit multi-output routing. The collection also includes application-facing counterparts to several WebView ideas. These are the repository's current implementations; their presence here does not make every attached transport exclusive to wgpu.

Current wgpu I/O architecture

Keep recording and external outputs from blocking the renderer #

Once an application has to record, stream, or share frames, the renderer should not wait for every external system to finish its work. The current wgpu I/O series solves that problem with a shared frame contract, bounded workers, and independent output sinks. It is one reusable architecture for a Rust-owned renderer; it is not a statement that the external transports require wgpu.

Native A/V Recorder

Record the GPU output and finish with a usable A/V file #

wgpu/43-wgpu-av-recorder is the focused starting point when your application needs native video recording with optional audio. It builds on the high-resolution recorder and adds three audio modes: none, microphone, and local audio file, then muxes the finished streams into the final file.

Microphone

CPAL captures the selected input to a temporary 32-bit float WAV while native video recording runs.

Audio file

FFmpeg-readable audio can be selected and looped when shorter than the video recording.

On successful mux the intermediate video and temporary microphone file are removed; failures preserve intermediates for diagnosis.

Status & validation

Know what was actually tested before you build on it #

Junkpile separates “the source exists” from “this path was actually exercised.” Use these status levels to decide whether an example is a stable starting point, a platform-specific reference, or still research.

Evidence Meaning
Source present Project exists in the tree.
Static validation Source/config/metadata checks exist; often documented in VALIDATION.md.
Runtime tested A named platform/device path was actually exercised.
Cross-platform tested Behavior was verified across the targeted operating systems.
Unresolved Project remains useful research but should not be used as a stable baseline.
Current exceptionsExample 29 is absent/quarantined by later documentation. Example 40 remains unresolved. Syphon and Spout are platform-specific. NDI-enabled builds require external SDK/runtime support.

Development

Change the example without losing the working reference #

A working example is most useful when you can tell whether your change caused the failure. Keep the original behavior easy to reproduce, then change one boundary at a time.

  1. Launch the untouched example.
  2. Confirm its documented input/render/output path.
  3. Preserve the baseline in version control.
  4. Change one ownership boundary at a time.
  5. Keep external workers bounded and observable.
  6. Record platform/dependency evidence when claiming validation.

See DEVELOPMENT.md and ADDING_AN_EXAMPLE.md.

Troubleshooting

Find which layer actually failed #

Do not debug the entire application at once. First decide whether the problem belongs to the WebView, the native GPU path, or an external I/O worker, then inspect the tools and state owned by that layer.

WebView

Console, shader compile/link, media permission, browser texture upload, WebSocket state.

Native GPU

Adapter/backend, surface state, bind groups, buffer alignment, texture formats, resource usage.

I/O worker

Readback slots, CPU pools, bounded queues, FFmpeg stderr, SDK/runtime dependencies.

See the full troubleshooting guide.

Glossary

Core terms #

Authoritative texture
The renderer-owned GPU image that represents the canonical frame before presentation/output-specific adaptation.
Bounded queue
A queue with a fixed capacity so slow output work produces visible pressure/drops rather than unbounded memory growth.
WebView
The embedded browser engine that renders HTML/CSS/JavaScript inside a desktop application.
wgpu
Rust graphics API used by Junkpile's native renderer path over Metal, Vulkan, and Direct3D 12.
WGSL
Shader language used by the native wgpu projects.
Readback
Copying GPU texture/buffer data into CPU-visible memory, commonly required by encoders or external APIs.
Sink
An independent consumer of rendered frames such as preview, recorder, NDI, Syphon, or Spout.
Last-known-good
A runtime configuration/shader strategy that rejects invalid edits while preserving the previous working state.
